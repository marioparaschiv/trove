## Facts in the code (trove-v1)
- `Indexer::standard` (`crates/trove-core/src/indexer.rs`) is `[Chunker]`; append the link parser as its own file in `indexer/`. `NoteFile` has `id`, `title`, `text`, no path. The `files` row (with `properties` JSON) is already written in the same transaction.
- Chunk ids are unstable: `Chunker::process` deletes and reinserts a note's chunks, ids change on every re-chunk, SQLite reuses the highest ids. `index_sources` (`indexer/scan.rs`) re-processes every note each run (S8 adds the skip).
- `edges` table: `(src, dst, kind, weight)`, PK `(src, dst, kind)`, kinds limited by CHECK. Nothing cleans edges when files/chunks go. Schema change needs `SCHEMA_VERSION` bump plus migration.
- Pipeline in `search/request.rs`: `Meaning` (z-scores, `MIN_Z = 2.5`) then `CollapseToNotes`; graph stage goes between. `Candidate` defined in `search.rs`, constructed in `search/meaning.rs` and `crates/trove-core/tests/search_pipeline.rs`.
- Existing tests the graph stage must keep passing (`crates/trove/tests/meaning_search.rs`): after restoring Beekeeping.md from `.trash`, HIDDEN_TOPIC returns exactly `["Beekeeping.md"]`; MATCHES_NOTHING returns `{"results": []}`; each paraphrase finds its note first. So the graph stage needs a threshold that stops it adding pure semantic neighbours.

## Draft design (not implemented)
- Node keys: `note:<file_id>`, `section:<chunk_id>`, `tag:<lowercased>`. Links store unresolved `ref:<target as written, with #heading or #^block>`, resolved at graph build (target may not be indexed yet). Resolution: `./`/`../` relative to linking note; else exact path; else by file name (same folder first, then shortest path), case-insensitive, `.md` optional. Heading target -> matching chunk; block target -> chunk containing `^id`; fallback to note.
- Link parser (after Chunker): delete the note's own `link`, `property_link`, `tag` edges plus semantic edges touching its current chunk ids (covers id reuse). Insert wikilinks and embeds (`link`, 1.0), markdown links to vault files (`link`, 1.0), tags from body and `tags` property (`tag`, 0.5, via tag node), links in other properties (`property_link`, 1.0). Skip frontmatter and code. Check weights against the spec "Graph" section.
- After `embed_missing`: delete edges whose note/chunk no longer exists; compute semantic edges: each chunk to its 10 nearest chunks in other notes above a cosine floor (measure on the fixture first).
- In-memory graph: petgraph 0.8.3 in workspace deps. Note, section, tag nodes; section-to-note membership edges. Co-citation/coupling computed at build, not stored, so editing one note never changes others' rows. Undirected; semantic pairs both directions keep the larger weight.
- PageRank: hand-written (petgraph's `page_rank` is not personalised or weighted). Restart 0.15, 20 iterations, dangling mass back to seeds. Test on a non-bipartite graph (bipartite can be ~4% off at 20 iterations); compute exact values by hand.
- Graph stage: score = `(1-W)*score/max + W*ppr/max_ppr`, W < 0.5 so a direct top hit stays on top. Non-hit sections added when above a threshold, flagged as graph. Graph rebuilt from SQLite per query.
- Why: `Candidate.graph: bool` exposed as `why: ["graph"]`, reconciled with S7's why shape (see S7 state; if S7 is merged first, use its shape directly).
- `--no-graph`: CLI flag plus request field (e.g. `no_graph`); then `bun run typecheck`, `lint`, `test`, `build` in `clients/`.
- Fixture/tests: add new hub notes only, each on its own topic linking to unrelated notes, one link kind per target. Each target appears with `why` containing "graph" (heading target lands on that heading) and disappears with `--no-graph`. Editing a hub to drop one link removes that target while other notes' links keep working. Rerun `meaning_search` after adding notes.
